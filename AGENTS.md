## Генерация коммитов

Проанализируй все незакоммиченные изменения и сгенерируй текст коммита.

### Требования

1. Ответ на русском языке.
2. Структура: заголовок → пустая строка → список изменений.
3. Заголовок: краткий, ≤40 символов, без точки в конце, user-friendly.
4. Описание: каждый пункт начинается с `- `, заканчивается точкой.
5. Группируй связанные изменения, не дублируй.
6. Не используй низкоуровневые технические детали, если их можно описать проще.
7. Явно указывай рефакторинг/оптимизацию/исправление ошибок.
8. Не используй markdown-заголовки, кавычки, вступления или заключения.
9. Ответ должен содержать только готовый текст коммита.

## Формат текста для Pull Request

### Структура

PR должен содержать следующие разделы:

1. **Описание** — одно-два предложения о том, что делает PR.
2. **Изменения** — список изменений по модулям/областям с краткими пояснениями.
3. **Файлы** — итоговая статистика (количество файлов, +/- строки).

### Правила

- Язык — русский.
- Описание — ёмкое, без воды.
- Каждый пункт изменений — с заголовком области (Экран, Домен, ViewModel, Core, Зависимости и т.д.) и списком конкретных изменений через `-`.
- Не перечислять каждый файл отдельно — группировать по логическим блокам.
- Указывать version bump'ы зависимостей, если они есть.
- Не включать код в описание (только если явно не попросят).

## Описание задач (Epic / User Story / Task)

Когда пользователь просит «описать задачу» (в любой формулировке: «опиши задачу», «разбей на задачи», «составь план задачи»), составь полноценную иерархию задач для внесения в систему контроля проекта.

### Классификация уровней

Обязательна трёхуровневая иерархия: **Epic → User Story → Task**.

**Epic (Эпик)**

- **Что это:** крупная бизнес-цель, модуль или целостная функциональность продукта.
- **Масштаб:** не помещается в один спринт (итерацию) — от 2 недель до нескольких месяцев.
- **Классифицировать как Epic**, если верхнеуровневая задача затрагивает разные слои системы (БД, бэкенд, фронтенд) и содержит более 3 независимых сценариев использования.
- **Шаблон названия:** `[Название модуля]: [Краткое описание сути]`, например `Авторизация: Система регистрации и управления профилями пользователей`.

**User Story (Пользовательская история)**

- **Что это:** мелкая функциональная часть Epic'а, приносящая конечную ценность пользователю или бизнесу.
- **Масштаб:** полностью помещается в один спринт — от 1 до 5 дней работы.
- Каждая история обязана соответствовать критериям INVEST (особенно: независимость и тестируемость). Результат User Story можно продемонстрировать на демо.
- **Строгая формулировка-тройка «Как — Я хочу — Чтобы»** кладётся в поля шаблона `user-story.md`: «Роль» ← *Как* [роль пользователя], «Потребность» ← *Я хочу* [выполнить действие / получить функцию], «Ценность» ← *Чтобы* [достичь бизнес-ценности / решить проблему].
- Написание истории от лица разработчика запрещено (см. «Критические ошибки декомпозиции»).

**Task (Техническая задача)**

- **Что это:** конкретное атомарное действие, необходимое для реализации технической части User Story.
- **Масштаб:** от 2 часов до 1–2 дней. Если техническая задача занимает более 16 рабочих часов — декомпозируй её на подзадачи.
- Пишется на техническом языке для разработчика и не несёт самостоятельной ценности для бизнеса без остального контекста Story.
- **Шаблон формулировки названия:** `[Направление] Глагол в инфинитиве + объект + контекст`, например `[Backend] Создать API-эндпоинт POST /api/v1/auth/reset-password для генерации токена сброса`.

### Процесс

1. До формирования текста загрузи через инструмент `skill` и строго следуй процессным скилам superpowers: `brainstorming` — уточнение требований, `writing-plans` — декомпозиция. Общее правило — `using-superpowers`: если скил применим к задаче, используй его.
2. Определи масштаб входного запроса: это уровень Epic, User Story или уже атомарная Task? Если запрос уже атомарен — не выдумывай иерархию сверх него.
3. Собери иерархию: 1 Epic → N User Stories → задачи (Tasks) для каждой User Story.
4. Заполняй шаблоны из `.github/ISSUE_TEMPLATE`: `epic.md`, `user-story.md`, `task.md`. Структура этих шаблонов — единственный источник истины для формата вывода: не изобретай собственную markdown-структуру и не подмешивай другие описания формата.
5. Выдавай результат поэтапно с согласованием на каждом уровне: сначала Epic, затем User Stories, затем Tasks. После каждого уровня дождись одобрения.
6. Каждый уровень — полностью заполненный markdown по своему шаблону: фронт-маттер (title, labels, assignees) и все секции. HTML-комментарии-подсказки в результате удаляй. В Task'е обязательно заполняются `labels` (по таблице лейблов), SP (по таблице оценки), `размер` (по таблице размеров XS–XL) и `приоритет` (по таблице приоритетов P0–P3); эти поля не используются для US и Epic.
7. Указывай связи между уровнями: в Task — родительская User Story, в User Story — Epic. Ссылайся по названию (номера присваивает трекер). Кроме иерархических связей фиксируй блокировки: в Task и US — по номерам (`TASK-1.1`, `US-N`), в Epic — по названию (номера присваивает трекер); записывай их в обеих сторонах — в блокируемой «Блокируется», в блокирующей — «Блокирует». Кросс-эпиковые блокировки (задачи или US разных эпиков) переноси на уровень эпиков: блокирует один эпик другой. Шаблоны `.github/ISSUE_TEMPLATE` не изменяй: блокировки записываются только в итоговый файл плана (см. п. 10).
8. Приоритизация в бэклоге идёт по правилу P0 > P1 > P2 > P3: при конфликте задач в первую очередь выполняются более высокие приоритеты; задачи одного приоритета — по порядку в бэклоге.
9. Текст — на русском языке.
10. После формирования и согласования всех Epic/US/Tasks запиши итоговый план в локальный файл проекта `docs/plans/<тема-латиницей-kebab-case>.md` (по образцу `docs/plans/tasks-view-and-management.md`). Структура файла: Epic → US → Tasks с нумерацией `US-N` и `TASK-N.M`; у каждой US и Task — строка `**Связь:**` с указанием родителя, а сразу после неё — поля блокировок `**Блокируется:**` / `**Блокирует:**` (по правилам п. 7: для задач и US — по номерам, для эпиков — по названию). Содержание уровней формируется по шаблонам `.github/ISSUE_TEMPLATE`, блокировки добавляются только в этот итоговый файл. Если у US или Task блокировок нет — записывай оба поля с прочерком (`**Блокируется:** —`).

### Критические ошибки декомпозиции

- **Технические User Story:** запрещено писать историю вида «Как разработчик, я хочу настроить Docker...». Переписывай это в Tasks внутри бизнес-историй или в технические Epic'и.
- **Размытые задачи:** избегай формулировок вида «Сделать фронтенд». Пиши конкретно: «Сверстать UI-компоненты для формы ввода OTP-кода по макету Figma».
- **Слишком крупные задачи:** если в списке Tasks есть пункт, занимающий весь спринт — декомпозиция провалена, пересобери структуру.
- **Собственный формат вместо шаблонов:** каждый уровень выводится строго по своему файлу из `.github/ISSUE_TEMPLATE`; не заменяй его произвольной markdown-структурой.

### Декомпозиция User Story → Tasks

Правила, одинаково понятные человеку и агенту:

- Каждая таска оформляется строго по обновлённому шаблону `.github/ISSUE_TEMPLATE/task.md`.
- Раздел «Технический контекст и ограничения» — только архитектурные рамки и связанные модули. Это не пошаговый план: не описывай, какие методы, классы или файлы создавать.
- Раздел «Критерии приёмки» — наблюдаемый конечный результат (что должно работать), а не последовательность действий исполнителя.
- Не навязывай исполнителю реализацию: конкретные решения и структура кода остаются за разработчиком.
- На этапе декомпозиции US продумывай порядок выполнения: если задача может быть начата только после другой — зафиксируй блокировку с обеих сторон по номерам (в блокируемой: `**Блокируется:** TASK-1.2`, в блокирующей: `**Блокирует:** TASK-1.3`). Пиши её только в итоговом файле плана (п. 10), не в шаблонах. Задачи без связей выполняются параллельно — не выдумывай зависимости без реальной последовательности.
- Блокировки поперёк разных User Story не описывай на уровне задач: переноси их на родительские User Story (`**Блокируется:** US-2` / `**Блокирует:** US-1`). Кросс-эпиковые зависимости переноси на уровень эпиков (см. п. 7).

Формулировка-триггер для агента:
«Декомпозируй эту User Story на таски по обновлённому шаблону. В разделе „Технический контекст“ укажи только архитектурные ограничения и связанные модули. В разделе „Критерии приёмки“ сфокусируйся на конечном результате (что должно работать), а не на последовательности действий. Не расписывай, какие методы создавать в коде.»

### Оценка трудоёмкости (SP)

SP назначаются только Task'ам (не US и Epic). Используется ряд Фибоначчи.

| SP | Ориентировочный объём |
|----|------------------------|
| 0.5 | Микрофикс: опечатка, правка одной строки/конфига |
| 1 | Тривиальная задача без рисков |
| 2 | Простая задача: правки в пределах одного модуля |
| 3 | Средняя задача: один модуль, есть нюансы/стыковка с API |
| 5 | Крупная задача: несколько модулей или интеграция |
| 8 | Очень крупная: межмодульная, требует согласования архитектуры |
| 13 | Масштабная, спорного объёма — требует декомпозиции |

### Размер задач (T-shirt)

Укрупнённая категоризация объёма (общепринятая в Agile — T-shirt sizing) для быстрой оценки и планирования. Задаётся для Task'ов совместно с SP.

| Размер | Ориентировочный объём | SP (примерно) |
|--------|------------------------|---------------|
| XS | Микрофикс: опечатка, правка одной строки/конфига | 0.5–1 |
| S | Простая задача: правки в пределах одного модуля | 2 |
| M | Средняя: один модуль, есть нюансы/стыковка с API | 3–5 |
| L | Крупная: несколько модулей или интеграция, нужна декомпозиция | 5–8 |
| XL | Очень крупная: межмодульная или масштабная, требует декомпозиции | 8–13 |

### Приоритеты задач

Приоритет определяет, насколько срочно нужно выполнять задачу, и влияет на порядок в бэклоге.

| Приоритет | Критичность | Когда берётся в работу |
|-----------|-------------|------------------------|
| P0 | Блокер: блокирует релиз или работу всех, деградация продакшена | Немедленно, вне спринта (hotfix) |
| P1 | Высокий: критично для ближайшего релиза/спринта | В текущем или ближайшем спринте |
| P2 | Средний: плановая работа, не блокирует остальных | По плану, в порядке бэклога |
| P3 | Низкий: желательная работа, некритичная | Когда есть свободный ресурс |

## Обзор проекта

Kotlin Multiplatform (KMP) проект — Web-приложение (JS) с JVM-таргетом для превью и тестов. UI на Compose Multiplatform, DI через Koin, навигация через Navigation3.

## Паттерны

- **API/Impl разделение**: каждый модуль фичи — `api` (интерфейсы, маршруты) + `impl` (экраны, фабрики)
- **Навигация**: фича реализует `FeatureNavModule` → `canResolve()` + `resolve()`
- **DI**: Koin, модули регистрируются в `DiProvider`
- **Сериализация маршрутов**: `@Serializable data object` для `NavKey`

## CI/CD

`pr-check.yml` запускается только на PR в `main` (JDK 21); триггера на push нет.
Шаги: `help` с `--warning-mode=fail` → `detekt` → `allTests` → сборка JS-дистрибутивов
`:webApp` (в `dist`) и `:webShell` (в `dist-shell`) с выгрузкой артефактов.

`cache-read-only` включён для PR-прогонов, так как кэш из `pull_request` доступен лишь
повторным прогонам того же PR; при единственном PR-триггере запись кэша сейчас не происходит.
`cleanup-caches.yml` раз в сутки (и по кнопке) удаляет записи кэша старше 14 дней.

## Тесты

### Именование

Имя теста — читаемая английская фраза в `backticks`, нижний регистр, без точки в конце:

```kotlin
@Test
fun `rejects negative version numbers`() { /* ... */ }
```

Требования к имени:

1. **Описывает поведение, а не механизм.** Имя должно отвечать на вопрос «что проверяется», а не «как устроен код». Сравнение версий — это `comparison depends on every version part`, а не `Equals test`.
2. **Начинается с подлежащего или глагола**, в зависимости от того, что важнее: активное действие — `parses valid version strings`, свойство — `equality depends on every part`.
3. **Конкретно, без общих слов.** Запрещены `test`, `test1`, `check`, `shouldWork`, `works`, `simpleValid`, `minValues`.

### Группировка

1. **Один тест — одно поведение.** Не создавай отдельный тест на каждый граничный случай.
2. **Однотипные случаи оформляй таблицей** в `private companion object` и прокручивай через `forEach`. Это проверяет общую логику и избавляет от разрозненных мелких операций:

```kotlin
@Test
fun `converts valid pass numbers to decimal numbers`() {
    CONVERSION_CASES.forEach { (pass, expected) ->
        assertEquals(expected, PassNumber(pass).toDecimalNumber(), "Неверная конвертация для '$pass'")
    }
}

private companion object {
    val CONVERSION_CASES = listOf(
        "0/0" to "00000000",
        "1/1" to "00065537",
    )
}
```

3. **Сообщения ассертов — на русском** и включают входные данные, чтобы по падению было видно, какой случай сломался.
4. Если набор разнородный — группируй по правилу, а не по количеству: «пустой ввод», «превышение диапазона», «неверный формат».

## Добавление фичи

1. Создать `features/<name>/api` с маршрутом (`@Serializable data object ... : NavKey`)
2. Создать `features/<name>/impl` с `FeatureNavModule` и экранами
3. Зарегистрировать модуль в `DiProvider`
4. Добавить модули в `settings.gradle.kts`
