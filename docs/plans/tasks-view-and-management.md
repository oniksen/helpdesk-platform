# План: улучшение списка задач и управление задачей

## 🚀 Эпик: Задачи: просмотр и управление

### 🎯 Глобальная цель
Реализовать полноценный flow управления задачами: список с краткой полезной информацией на карточке, детальный экран с полной информацией и действиями по управлению задачей (жизненный цикл, параметры, создание).

### 🚫 Что НЕ входит в этот Эпик (Out of Scope)
- Внутренний чат задачи — выносится в отдельный Epic после этого плана.
- JVM-таргет — отдельный Epic «Задачи: функционал для JVM-таргета» (см. ниже), выполняется после roadmap, когда существующий настроенный JVM-таргет (`:jvmApp`) уже будет.
- Интеграция jvm-таргета в рамках этого эпика не делается — работа ведётся только над web-таргетом.

### 🏗 Архитектурные константы и подходы
- Весь код фичи (`features/tasks/impl`) лежит в `commonMain` — JS-специфика отсутствует, платформенная специфика только через expect/actual в core-модулях.
- Список: `TasksPageViewModel` (`BaseViewModel`), пагинация page/page_size через `TasksRepository.loadPage` → `GET /help-desk/v3/tasks/listing`.
- Навигация: `@Serializable data object : NavKey` в `features/tasks/api`, резолв через `FeatureNavModule`, регистрация в Koin (`FullAppDefinition`).
- API управления задачей на бэкенде уже существует — в задачах предусмотрены placeholders под ссылки на спецификацию.
- Стиль UI — Compose Multiplatform, адаптивность через `AdaptiveLayoutWrapper` (брейкпоинты 600/840 dp), Snackbar для ошибок.

### 📋 Критерии приёмки
- [ ] **Сценарий 1 (Успешный):** Дано: Пользователь находится на экране задач. Если: Список задач загружен. То: Пользователь увидит задачи с основной, динамически изменяющейся информацией.

- [ ] **Сценарий 4 (Негативный):** Дано: Пользователь листает список задач и доходит до конца текущей страницы. Если: Страница не загрузилась. То: Увидит всплывающее сообщение об ошибке с возможностью повторить загрузку страницы. Loading indicator при этом должен исчезнуть.
- [ ] **Сценарий 5 (Успешный):** Дано: Пользователь находится на экране задач и видит разные списки этих задач в зависимости от своей роли. Если: Пользователь меняет список задач (выбирает другой tab). То: Система подгрузит новый список с изменёнными фильтрами.

### TASK-1.1: Исправить подгрузку новой страницы списка задач
**Родительская US:** US-1
- **Приоритет:** P1
- **SP:** 5
- **Размер:** M
- **Лейблы:** bug, test, web

#### 📝 Описание задачи
Web-таргет, открытый в MAX-окружении на мобильной платформе, не подгружает новую страницу списка задач; в другом окружении web-таргет успешно её подгружает. Исправить механизм подгрузки, чтобы страницы догружались по требованию при прокрутке в любом окружении. Это необходимо, чтобы пользователь мог беспрепятственно листать весь список задач.

#### 🛠 Технический контекст и ограничения
- **Связанные компоненты:** `features/tasks/impl` — `presentation/viewmodel/TasksPageViewModel.kt`, `presentation/screen/compact/TasksPageContentCompact.kt`, `data/repository/TasksRepository.kt`.
- **Текущие проблемы:** подгрузка привязана к polling'у каждые 5 с (`flatMapLatest` + `delay(5000)`) вместо события скролла; расчёт номера страницы захардкожен под `page_size = 10` (`index % 10 < 3`), что ломается при другом размере страницы/окна; поле `loading` в `TasksPageState` объявлено, но не используется.
- **Ограничения:** пагинация page-based (`page`, `page_size`, `hasNext` из `Pagination`), offset не передаётся; дедупликация через `entityCache`/`filterCache` во ViewModel — сохранить подход.
- **Внимание:** проверить поведение в MAX-окружении (внутренний скролл Compose, `overflow: hidden` у страницы); не допустить двойных запросов одной страницы при быстром скролле.

#### 🧪 Критерии приёмки
- [ ] Страница списка запрашивается по достижении конца текущей страницы при прокрутке, без фонового polling'а.
- [ ] Номер запрашиваемой страницы вычисляется из фактического `page_size`, хардкода размера страницы нет.
- [ ] Поле `loading` в состоянии списка управляет видимостью индикатора в футере и исчезает после завершения загрузки (успех или ошибка).
- [ ] Добавлены unit-тесты на получение новой страницы (успешный переход на следующую страницу, отсутствие запроса при `hasNext = false`, повторный запрос после ошибки).
- [ ] `./gradlew allTests` и `./gradlew detekt` проходят.

### TASK-1.4: Обработать ошибку загрузки списка и пустой список

- [ ] Повторная попытка запрашивает ту же страницу; успешный повтор добавляет элементы в список.
- [ ] Уже загруженные элементы не теряются при ошибке догрузки.
- [ ] Добавлены unit-тесты обработки ошибок (первая страница, догрузка, повтор).
