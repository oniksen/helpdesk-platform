# Дизайн: вход по email и паролю в desktop-приложении (JVM)

Дата: 2026-11-25. Ветка: `feature/jvm-password-auth`. Статус: на согласовании (пересмотр спринтов).

## 1. Цель и зачем

Desktop-приложение должно позволять пользователю войти по email и паролю и запомнить сессию. Сейчас задачи доступны только авторизованному пользователю, а авторизация в web происходит автоматически через окружение MAX, которого в JVM-окружении нет и не будет по замыслу. Без отдельного экрана входа desktop-версией нельзя пользоваться.

Итог: пользователь запускает приложение, вводит email и пароль, получает Bearer-токен и работает с задачами. Если включён «Запомнить», при следующем запуске ввод не требуется, пока токен действителен.

## 2. Границы

### 2.1 Входит в scope

- экран входа для JVM: email, пароль, «Запомнить», валидация, загрузка, сообщения об ошибках;
- платформенный выбор режима входа: web — MAX как сейчас, JVM — email и пароль;
- вызов серверного эндпоинта авторизации и получение Bearer-токена;
- сохранение токена и email пользователя в файле в пользовательском каталоге приложения;
- восстановление сессии при запуске и выбор стартового маршрута;
- обработка отсутствующего, повреждённого и истёкшего токена;
- тесты и приёмка на Windows и macOS.

### 2.2 Не входит в scope

- вход по паролю в web, регистрация, восстановление пароля, 2FA, SSO;
- серверные изменения и новые контракты API;
- хранение пароля в любом виде;
- финальный дизайн экрана — доработки внешнего вида переносятся в следующие версии;
- SQLDelight и offline-режим — планируются в следующих релизах, если подход понадобится;
- шифрование файла с токеном (см. раздел 6).

### 2.3 Anti-goals

- пароль не сохраняется, не логируется и не остаётся в состоянии после отправки;
- вторая параллельная сессия не появляется: источник токена один на платформу;
- данные задач не показываются без действующего токена;
- web не получает вторую форму входа и продолжает работать через MAX;
- JVM-граф зависимостей не обращается к MAX-мосту.

## 3. Ограничения и контракты

- Общий код живёт в `commonMain`; JVM-специфика — в core-модулях и точке входа `jvmApp`.
- Серверный эндпоинт авторизации возвращает Bearer-токен (и небольшой набор данных). Точный путь, формат тела и ошибок фиксируются в коде как DTO на этапе реализации.
- Профиль пользователя получается по email после авторизации: авторизация возвращает Bearer-токен, затем по email запрашиваются данные пользователя (роль, уровень доступа, корпуса, сервисы). Поэтому в файле помимо токена сохраняется email. Пароль в файле не хранится и вводится пользователем при необходимости.
- Запрос данных пользователя должен идти по Bearer-токену, а не по статическому `api_key` (#164): ключ отзывается в #160, и вход не может от него зависеть.
- Логирование заголовков и тел запросов отключается до включения входа (#165): иначе `Authorization` попадёт в консоль и файлы логов.
- Срок жизни токена определяется сервером: токен содержит информацию об истечении, но парсинг и проверка свежести происходят на сервере при запросе. При первом неудачном запросе возвращается ошибка истечения токена. Локально срок не вычисляется и в файл не записывается.
- Выход из аккаунта и обработка 401/403 выполняются по #167.
- Деплой выполняется через собственную систему компании и занимает не более суток; проверка и выкладка укладываются в один рабочий день.
- Ёмкость — 40 SP на итерацию. Каникулы 31.12.2026–10.01.2027 нерабочие, первый рабочий день — 11.01.2027.

## 4. Рассмотренные подходы

### 4.1 Как выбирается режим входа

| Вариант | Суть | Оценка |
|---|---|---|
| **A. Один экран + платформенная стратегия** | Платформа через DI поставляет стратегию: JS — MAX, JVM — email и пароль. Общий ViewModel и состояние, различается источник токена | **Выбран.** Минимум дублирования, одна точка входа, не ломает web |
| B. Отдельная JVM-фича | Свой экран и ViewModel только для desktop | Дублирует состояние, эффекты и обработку ошибок; два разных входа в приложение |
| C. Форма как реакция на `Unavailable` от MAX | JVM-реализация MAX возвращает «недоступно», ViewModel показывает форму | UX завязан на ошибку; противоречит #149, который убирает MAX-мост из JVM-графа |

### 4.2 Где хранится токен

| Вариант | Суть | Оценка |
|---|---|---|
| **A. Обычный JSON-файл** | `save/load/clear` строки в пользовательском каталоге приложения, права только у владельца | **Выбран.** `AuthStateStorage` уже описан как строковое хранилище; 0,5–1 SP на реализацию |
| B. Системное хранилище ОС | Windows Credential Manager, macOS Keychain через `javakeyring` | Отклонён владельцем: сложнее, а отзыв токена всё равно остаётся основным средством реакции |
| C. Шифрованный файл | AES-GCM с ключом, привязанным к машине | Ключ всё равно нужно где-то хранить; защита сводится к системе, лишний слой |
| D. SQLDelight | Таблица на одну запись в SQLite | SQLDelight в проекте отсутствует; на диске файл такой же открытый. Планируется позже под offline-режим |

## 5. Принятые решения

### 5.1 Стратегия входа

- В `core/authorization` вводится контракт стратегии входа. Web-граф регистрирует MAX-стратегию, JVM-граф — парольную. `AuthorizationScreenViewModel` не вызывает MAX напрямую, а работает со стратегией.
- Режим определяет стратегия, а не факт ошибки. На JVM MAX не вызывается вообще.
- Реализация контракта, его имя и способ передачи режима в UI остаются за исполнителем.

### 5.2 Экран

- `AuthorizationScreen` / `AuthorizationScreenCompact` расширяются формой: email, пароль, чекбокс «Запомнить», кнопка входа, индикатор загрузки и snackbar ошибок.
- Валидация: пустой email, email без `@`, пустой пароль — до отправки запроса.
- Пароль очищается после отправки и никогда не попадает в состояние, эффекты и логи.
- «Запомнить» выключен по умолчанию: без него токен живёт только в памяти до закрытия приложения.
- Дизайн экрана не финальный: доработки внешнего вида переносятся в следующие версии; в этой итерации достаточно рабочего варианта по существующему макету.

### 5.3 Сессия

- JVM-реализация `AuthStateStorage` пишет JSON с токеном и email пользователя в файл в пользовательском каталоге приложения. Срок истечения в файле не хранится: он определяется сервером при запросе.
- Права: на macOS файл создаётся с `0600`; на Windows используется каталог профиля пользователя, который уже ограничен ACL. Точный путь выбирает исполнитель.
- Данные пользователя (роль, уровень доступа, корпуса, сервисы) при восстановлении запрашиваются по email и токену; в файле их нет.
- Повреждённый или пустой файл считается отсутствием сессии: файл удаляется, показывается вход.
- `maxInitData` и cookies в JVM-состояние не попадают. Пароль нигде не хранится.

### 5.4 Старт и истёкший токен

- При запуске: есть валидный сохранённый токен → экран задач; нет или истёк → экран входа.
- 401/403 на любом запросе → очистка файла и состояния в памяти, переход на вход один раз, без цикла повторных запросов.
- В JVM-клиенте установлен плагин `HttpRequestRetry` (5 повторов с растущей задержкой). Нужно убедиться, что 401 не попадает в политику повторов, иначе истёкший токен будет повторяться 5 раз перед ошибкой. Это решается в TASK-2.2 и #167.
- Если сервер не отдаёт срок жизни токена, единственным признаком истечения остаётся 401/403.

### 5.5 Выход

- Выход удаляет файл и очищает состояние в памяти, затем открывает экран входа. Поведение реализуется вместе с #167, чтобы web и JVM не расходились.

### 5.6 Логи

- До включения входа отключается логирование заголовков и тел запросов в релизной конфигурации (#165). Токен и пароль не должны попадать в консоль, `stdout` и файлы логов.

## 6. Принятый риск

Владелец продукта сознательно принял хранение Bearer-токена и email пользователя в открытом виде в пользовательском каталоге. Последствия:

- любой процесс под той же учётной записью может прочитать токен и действовать от имени пользователя; вместе с токеном в файле лежит email, что связывает токен с учётной записью;
- отзыв токена помогает только после обнаружения компрометации, а обнаружение не автоматизировано;
- срок жизни токена определяется сервером; локальной проверки свежести нет, поэтому истёкший токен обнаруживается только по ошибке запроса.

Компенсирующие меры, которые остаются в силе: пароль не хранится, токен не логируется, файл доступен только владельцу, выход удаляет токен и email, состояние сессии минимально.

## 11. Риски

- Открытый файл с токеном: компрометация возможна без следов, реакция — только отзыв (раздел 6).
- Срок жизни Bearer неизвестен. Если он короткий, «Запомнить» будет часто возвращать на вход — это нужно отразить в тексте экрана.
- #164, #165, #167 не запланированы в итерациях. Если они не попадут в Iteration 36–37, сдвигается весь эпик.
- Iteration 38 перегружена: 37 SP при 8 рабочих днях. Критическое условие: #129 должна завершиться 20.12, иначе TASK-2.1 не стартует 21.12. Запасного дня почти нет.
- Эндпоинт авторизации не описан в репозитории: ошибка в DTO обнаружится только на интеграции.
- На macOS файл может наследовать неожиданные права при копировании профиля; проверка входит в TASK-3.1.
- В JVM-клиенте установлен плагин `HttpRequestRetry` (5 повторов с растущей задержкой). Нужно убедиться, что 401 не попадает в политику повторов, иначе истёкший токен будет повторяться 5 раз перед ошибкой. Это решается в TASK-2.2 и #167.
- Оптимистичные оценки: если разработка займёт больше запланированного, релиз сдвигается на 22.01.2027.
